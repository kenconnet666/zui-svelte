# Core 运行时 CSS 设计草案

状态：运行时自动提升方向已确认，公开 API 与生产合同继续讨论。2026-09-17。
本文件描述设计，不代表已经实现。选择器、多部位组件、组合顺序、参数和首版 SSR 的深入讨论见 [生产级组合设计](core-composition.md)，类型生成与主题见 [类型与主题设计](core-types-theme.md)。新讨论与早期 API 草图不一致时，以新文档明确的约束为准。

## 1. 已确定的产品方向

- 框架无关的 TypeScript core，自有 CSS runtime，使用 Stylis 处理 CSS。
- 使用者正常编写 ICSS，不需要声明 dynamic、传动态 getter、维护变量字典或判断更新频率。
- 动态声明由运行时自动识别；稳定结构中的动态值提升为元素级 CSS 变量。
- 普通值初次保持静态；同一绑定中首次检测到值变化才尝试提升，不分析响应式来源，不预先参数化全部普通值。
- Svelte 层负责响应式订阅与 DOM 生命周期，core 不导入 Svelte。
- css() 返回原始字符串，公开使用 class；编译器负责 class 与内联变量、SSR、生命周期的桥接，运行时负责输出比较和自动提升。未接入编译桥时保留完整规则路径，不输出依赖缺失变量的样式。
- 暂不移植旧仓库的完整主题、组件、编译器和审计脚本。
- 首版以生产使用为目标；SvelteKit/SSR 消费、hydration 与请求隔离属于验收范围，文档站仍为普通 Svelte + Vite。

## 2. 先区分三个概念

| 概念         | 含义                                                 | 所属                 |
| ------------ | ---------------------------------------------------- | -------------------- |
| StyleProgram | 一次样式回调执行后的有序声明描述                     | core                 |
| RuleRecord   | 注册在某个样式作用域内的不可变共享规则               | core                 |
| StyleBinding | 一个元素上的持续样式实例，持有上次结果、动态位置和值 | core；由 Svelte 驱动 |

初次只拿到 width=120 无法知道它未来是否变化。必须在同一个持续绑定内观察不同执行结果。

样式规则共享不等于实例历史共享。不同元素的变化记录独立；规范化后的相同规则可以共享。不要用函数源码、调用栈、临时回调对象地址推断样式实例身份。

## 3. 已确认的公开接入方向

用户只绑定 class；css() 返回原始字符串，不返回 StyleHandle、parts 对象或 attachment。

```svelte
<div
  class={css((s) => {
    s.width.px(width);
    s.gap.px(12);
  })}
>
  ...
</div>
```

多个 class 可独立拼接、条件选择和转发，不强制预组合。普通 TS 函数可以接收参数并返回 CSS class。

组件 class 控制根元素；slotProps 转发子元素/组件的参数、class、style 和允许的事件属性。不存在 core 统一命名样式部位的前提。

编译阶段在 client/server 生成隐藏绑定。它不分析每个值是不是响应式，而是关联 class 的消费目标、变量结果和生命周期。

原始字符串不能自行改变。动态调用放模板表达式或 Svelte 标准 $derived；普通 const 保持快照语义，若要自动改写需另定编译合同。

内部共享规则与样式实例必须分开标识；是否通过额外绑定标记 class 传递仍待讨论。详见 [class 与 slotProps 设计](core-composition.md)。

## 4. ICSS 的表达范围

沿用已有项目的语句式载体方向：

```ts
(s) => {
  s.display.flex;
  s.width.px(width);
  s.color._primary;
  s.opacity(opacity);
};
```

- 关键字、Token、单位保留强类型提示。
- 属性值调用只记录数据，回调收集期间不改 DOM。
- 回调应为纯样式计算，可重复执行，禁止依赖一次性副作用。
- 单位归一化发生在比较前；120px 和内部不同表示归一为同一比较值。
- undefined/null 表示省略声明时，需要进入结构处理，不能简单清掉变量后继续保留原声明。
- 同一属性的多次声明有顺序语义，不能用普通对象覆盖掉前项。
- selector、媒体条件、supports 条件及声明顺序都是结构的一部分。

属性 metadata 是关键字、Token 类别与单位约束的单一来源。首批选择高频属性验证载体，避免先生成全量 API 再发现模型不适用。

## 5. 内部数据与序列化

StyleProgram 建议采用有序树，叶子记录 property、value、important，内部节点记录 selector 或 at-rule。

区分两个比较维度：

- 结构描述：节点类型、选择器、条件、声明位置、属性、优先标记。
- 规则内容：结构 + 仍静态的值 + 动态位置掩码。

规则 key 不能仅基于“属性名列表”。两个尚未变量化的 width:120px 和 width:240px 不能误用同一条固定值规则。

规范化需要保留声明及条件块顺序。不排序可能改变回退、简写覆盖或层叠的声明。hash 冲突后比较规范化内容，不能只相信短 hash。

第一版以结构化数据比较为主，不比较最终拼接的大字符串，也不在每次值更新时调用 Stylis。

## 6. 自动提升流程

### 首次绑定

1. 同步执行回调，收集并规范化 StyleProgram。
2. Token 已解析为主题变量引用；普通值先保持静态。
3. 注册或复用静态规则，绑定到元素。
4. 保存结果作为后续比较基线。

### 后续执行，结构一致

1. 按声明位置比较规范化值。
2. 首次发生变化且满足提升条件的位置，加入动态集合。
3. 生成或复用新规则；动态位置使用内部变量，静态位置仍包含原值。
4. 写入当前实例的全部必要变量，在同一次提交中迁移受控 class。
5. 释放旧规则引用。
6. 之后该结构的动态集合不变时，只更新变化的变量值。

已确认“第一次不同即提升”的方向，不使用毫秒窗口或快速变化计数。switch 不同分支若生成相同结构、不同值，也可以提升；无需识别源码分支或响应式来源。多个值一起变化也分别处理，变化条数不作为复杂度判断。已知变体仍可以通过 recipe 或状态规则处理，但不把这种区分暴露成用户必须写的动态提示。

### 后续执行，结构变化

- 获取该结构对应的规则与提升记录；只重建当前绑定受影响的部分。
- 删除不再属于新绑定的变量，释放旧规则引用。
- 简单方案按结构保存有限历史；短暂切换回旧结构时可复用提升记录。
- 每绑定结构历史采用有界缓存；缓存具体容量待基准测试确定。
- 禁止每遇到新值就永久保留一个规则或一个历史节点。

规则迁移不能修改其他实例正在共享的 RuleRecord。动态掩码变化可能产生新规则版本，但共享记录保持不可变。

## 7. 可以提升和暂不提升的内容

| 情况                                           | 第一版处理                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| 有效的数值、长度、颜色、完整 transform 值      | 满足比较条件后自动提升                                               |
| 已是主题变量引用                               | 继续通过主题变量解析，避免无意义的变量套变量                         |
| 同结构下修改引用的主题 Token                   | 按规范化值处理，保留 Token 依赖语义                                  |
| :hover / ::before 内的值                       | 同一元素作用域且声明有效时可提升                                     |
| 媒体查询内部的声明值                           | 可以提升，媒体条件保持结构                                           |
| 媒体条件、选择器、属性名变化                   | 结构变化                                                             |
| null/undefined 导致声明省略                    | 结构变化                                                             |
| CSS 全局关键字 initial/inherit/revert/unset 等 | 保留原声明语义，第一版不自动提升                                     |
| 重复回退声明、混合简写/长写、未知 raw 值       | 保守回退到规则更新，先验证等价性                                     |
| 任意后代/兄弟选择器中的值                      | 第一版限制自动提升范围或建立明确目标绑定，不能假设根变量总能正确到达 |

“自动”不等于牺牲 CSS 语义。无法安全提升时继续自动更新规则，不要求使用者补一个 dynamic 标记。

CSS 变量的替换发生在计算值阶段。原本在解析阶段被忽略的无效声明，变量化后可能使整个属性失效。CSS.supports 也不足以证明所有含 var()、回退与简写的场景都等价。

清理变量不是删除声明：width:var(--x) 在变量缺失时仍存在于层叠中。因此属性删除必须改变规则结构，不能仅 removeProperty('--x')。

## 8. 作用域、层叠与 DOM 所有权

### 样式表作用域

每个 Document、ShadowRoot、SSR 请求拥有各自 registry。禁止全局单例直接捕获 document。

规则有活动引用计数，零引用后回收；若增加热缓存必须有界。HMR 可以按模块 owner 释放，但 owner 设计不依赖不稳定堆栈。

### 元素所有权

绑定只改自己拥有的 class token 与内部变量，不设置整个 className，不覆盖整个 style.cssText。

允许多个独立 class 控制同一元素，不强制先合并。编译生成的内部协调者管理变量命名、消费引用与清理，覆盖保持 CSS 语义。

清理时还要考虑别人后来修改了同名属性：内部变量名避免外部共享；必要时仅在当前值仍由本绑定拥有时撤销或恢复。

### 变量继承

内部变量命名按规则/声明位置区分，不能只用 --width。

凡是绑定到带变量规则的元素，必须拥有完整的本地变量值，避免嵌套同类组件继承父实例值。没有当前值的声明通过规则结构处理，不以“删变量后回退到祖先值”代替。

Portal 必须在目标元素上绑定变量或显式传递主题作用域；组件树父子关系不等于 CSS 继承关系。

### 覆盖顺序

建议预留 reset、theme、components、overrides 的层次，但公开可配置层级待讨论。

变量化不应改变 specificity、important、规则相对顺序。迁移时把新规则简单追加到样式表末尾可能改变同优先级竞争结果，需要稳定的逻辑规则顺序。验收应检查计算样式，不能只检查字符串快照。

## 9. Svelte 求值与编译绑定

- 动态 class 表达式按 Svelte 正常响应式规则重新求值，TS helper 正常执行。
- 编译器为消费点建立持续绑定，内部比较历史不会因每次 class 求值而重置。
- 完整 class 字符串可能在变量变化后保持相同，变量提交必须有独立的内部版本通知。
- 消费点统一协调用户 class/style、多个受管 class、style: 指令及清理。
- class 转发到组件或 slotProps 后，变量应写到最终消费元素。
- client/server 变换一致；服务端收集与客户端接管使用同一套命名和初始静态结果。
- 不依赖 DOM 全局扫描恢复绑定，不让使用者手写内部变量或 getter。
- 无法确定稳定 identity 或接入边界时，回退到完整规则更新，不错误复用另一实例的历史。

回调执行、声明收集与比较仍有成本；自动提升减少规则生成与插入，不承诺零计算更新。

## 10. 主题与 Token

建议分三层：

1. 基础尺度：颜色、间距、字号、圆角等。
2. 语义 Token：primary、surface、text、border、focus 等。
3. 组件 Token：button 等具体组件的局部参数，定义在组件库。

core 提供主题定义、扩展、解析和 CSS 变量输出；不内置完整组件表。

推荐让稳定的 Token 引用直接生成 var(--z-theme-...)，主题切换更新主题作用域，尽量不重建全部组件规则。

API 需讨论：普通对象 + defineTheme，或 class Theme + 泛型扩展。倾向普通对象与少量明确函数；若类能显著改善类型扩展与生命周期，再选择类。

主题值通常不可原地悄悄修改：通过明确更新入口生成新解析结果。嵌套主题输出差异还是完整值，需要结合继承与清理验证。

## 11. SSR、CSP、HMR 的范围

文档站是客户端网站，但 core 的纯计算入口和 registry 必须能够在无 DOM 环境导入。

SSR 输出规则、class、初始变量与 hydration 信息需要独立合同；初始状态不得依赖客户端过去的变化次数。首屏 hydration 后再学习和提升，避免服务器与浏览器 class 不一致。

编译器同时生成 SSR class/style 输出、请求级收集与 hydration 接管所需桥接。普通 Svelte SSR 与 SvelteKit 消费均应验证；文档站不因此改用 SvelteKit。

严格 CSP 对样式标签、序列化 style 属性与 CSSOM 修改的限制不同，需要按具体策略测试。nonce 只覆盖样式标签，不代表所有内联输出已经被允许。

HMR 优先释放旧模块的规则与绑定关系，后续再考虑保留提升记录；正确性先于开发态缓存命中。

## 12. 性能目标与不作的承诺

稳定结构已经完成提升后：

- 规则数不随不同值数量线性增长。
- 值更新不再调用 Stylis、完整 CSS 序列化或规则插入。
- DOM 只写发生变化的内部变量。
- 规则与历史缓存有可解释的上限，卸载能释放活动引用。

仍然存在：

- 回调执行、声明收集与比较。
- 元素 style 写入。
- 浏览器样式计算；width 等属性还可能触发布局。

跨实例的高基数值是单独问题：一万个元素首次渲染各有不同宽度，不会因为单实例比较自动学会动态。第一版先保证零引用规则回收，后续评估共享模板值分布或更积极的参数化，不用虚构基准数字宣称已解决所有规模问题。

## 13. 必须验证的行为

1. 同一元素宽度连续更新 10000 次，提升后规则数稳定。
2. 两个元素初始共享规则，只有一个更新时另一个不变。
3. 先提升 width、后提升 opacity，旧版本安全释放。
4. 嵌套相同组件不继承父实例的内部值。
5. 悬停、伪元素和媒体条件内的提升前后计算样式一致。
6. null/undefined 删除声明后，外部样式正确接管。
7. 重复声明、简写、important、全局关键字、无效值保持原语义。
8. 条件块切换与回调替换不无限增长缓存。
9. 自有变量更新不清掉调用方 style/class。
10. 挂载卸载循环及 HMR 不遗留规则或事件资源。
11. ShadowRoot 与多个 Document 的作用域隔离。
12. 首版 SSR 中，首屏、hydration 与自动提升后的输出一致，并验证并发请求隔离。

第一阶段先做纯描述与比较测试；DOM 相关再用真实浏览器测试。回退规则也是正确实现，不用放宽语义换取“全自动”的表面覆盖率。

## 14. 推荐实施顺序

| 阶段 | 交付                                          | 验证                                      |
| ---- | --------------------------------------------- | ----------------------------------------- |
| C0   | 确定公开接入、Token 与自动提升边界            | 讨论本文                                  |
| C1   | 元数据生成、有序 StyleProgram、ICSS、值规范化 | 类型/runtime 一致、关键字、单位、声明顺序 |
| C2   | Stylis、registry、作用域、逻辑顺序与释放      | 去重、冲突、层叠、无 DOM 导入             |
| C3   | 持续绑定、结构比较、自动提升、差量写入        | 多实例、高频值、删除、复杂选择器          |
| C4   | class 编译绑定、slotProps 与参数              | 首屏属性、订阅、组合、销毁                |
| C5   | Theme、扩展类型、recipe 与部位定制            | 嵌套主题、变体、覆盖、Portal              |
| C6   | SSR 收集、hydration、CSP 与 HMR               | SvelteKit 消费、请求隔离、错误回滚        |
| C7   | Select/Dialog 等真实消费与外部 tarball        | 三浏览器、复杂组件、类型与包消费          |

编译绑定是公开 class-only API 的实现前提；不做响应式来源分析，不提供手动 dynamic/getter API。先验证字符串元数据、组件转发与 SSR 原型，再扩展实现。

这些是实现阶段，不是降低首版发布合同。首次生产发布必须完成生产级组合设计与类型主题设计中的必需验收，不能把某个早期阶段完成称为生产可用。

## 15. 当前决定与继续讨论的内容

1. 已确认：同一绑定、同一结构、首次值变化自动提升；无法保持语义时切换规则。不分析响应式来源，不要求用户标记动态值。
2. 已确认：首版需要支持 SvelteKit/SSR 消费。
3. 已确认：class 字符串、独立绑定、允许多 class 自由组合、普通 TS 参数函数、组件 slotProps；待讨论内部身份传递及编译边界，见生产级组合设计。
4. 待讨论：主题表示、扩展后类型传播、生成器输入与运行时一致性，见类型与主题设计。

这三项之外，目录、依赖和普通 Svelte 文档站已按当前约定建立，不需要重复确认。
